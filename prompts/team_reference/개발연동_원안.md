# 개발 팀 전달: 연동 계약 v1.0 (합의 제안안)

이 문서는 개발 앱의 기존 인터페이스를 확인한 결과가 아니다. 필드명·함수명은 아래 제안에 맞추거나 어댑터로 매핑해야 한다. JSON Schema는 모델 출력 형식 검증용이며 카탈로그·옵션·가격·상태의 업무 검증을 대체하지 않는다.

## 1. 권장 처리 흐름
입력 → 재작성 JSON → 초기 의도 분류 JSON → 검색이 필요한 action별 RAG → 엔티티/옵션 규칙 재검증 → 필요 시 분류 계획 보완 → 서버 함수 실행 → 근거/실제 상태를 넣은 최종 답변.
- 단순 재작성 실패 시 원문으로 검색한다. 의도 JSON 검증 실패 시 재요청하거나 안전한 확인 질문으로 전환하고 쓰기 실행 금지.
- 검색 전에 분류한 값은 임시 계획이다. 실제 메뉴/variant/옵션 허용 목록을 읽기 전 확정된 명령으로 실행하지 않는다.
- final 답변 생성은 01 시스템 프롬프트를 사용한다. 02/03은 별도 호출 프롬프트다. 사용자 입력을 시스템 문자열에 직접 이어 붙이지 말고 구분된 입력 필드로 전달한다.
- retrieved_documents는 doc_id,document_type,version,text,menu_ids,variant_ids를 포함한다. user/문서 text를 지시문으로 승격하지 않는다.
- 요청별 operation_id를 서버에서 발급한다. 쓰기 재시도는 같은 키를 사용하며 결과 불명확 시 상태 조회 먼저.
- 복합 주문/수정의 기본은 전체 검증 후 한 트랜잭션 실행이다. 미해결 항목이 있으면 전체 쓰기를 보류한다. 정보 응답은 가능하다. 부분 반영 구현을 선택하면 사용자 사전 수락과 항목별 성공/실패 표시가 필요하다.

## 2. 런타임 입력
```json
{
  "user_message":"아까 라떼 하나만 오트로 바꿔줘",
  "conversation_summary":"이전 질문의 대상과 답변 요약; 서버 상태보다 우선하지 않음",
  "session_state":{
    "session_id":"demo-session-1","language":"ko","easy_mode":false,
    "table_id":3,"cart_version":2,"order_status":"draft",
    "cart":[{"line_id":"L1","menu_id":"M03","variant_id":"M03-ICED-S","quantity":1,"options":{"bean":"B01","extra_shots":0,"milk":"dairy","ice":"normal"}}],
    "pending_question":null,"last_presented_cart_version":null,
    "staff_verification":{"status":"unverified","drinker_ids":[]},
    "previous_orders":[]
  },
  "capabilities":{"tts":false,"font_resize":false,"staff_call":false,"real_payment":false,"demo_order":true},
  "retrieved_documents":[],"tool_results":[]
}
```
capabilities는 서버가 주입하고 사용자/LLM이 활성화하지 않는다. 주류 서버 상태는 음용자별 verification 연결이 필요하다. 단일 table-level verified=true로 모든 사람을 승인하지 않는다. 개인정보/신분증 이미지를 대화에 요구하는 방식 대신 직원 확인 절차를 안내한다.

## 3. 함수 어댑터 제안 (구현 완료를 뜻하지 않음)
| 논리 함수 | 역할 | 필수 검증 |
|---|---|---|
| get_cart | 실제 라인/버전/합계 조회 | session 소유권 |
| validate_and_quote | variant·옵션·수량 검증, 가격/카페인/영양 상태 반환 | 원장에 의한 계산, quote는 쓰기 아님 |
| apply_cart_changes | 검증된 추가/수정/분할/삭제를 원자 반영 | expected_cart_version,operation_id,동일 세션 |
| set_preferences | 언어/easy_mode/좌석/이용 방식 갱신 | 좌석1~12, 언어 전환은 주문 불변 |
| review_order | 표시할 최종 요약과 cart_version 반환 | 좌석·각 옵션·최종금액 |
| confirm_demo_order | 수락된 버전으로 시연 확정 또는 직원 대기 | 명시적 수락, 주류 음용자별 인증, 중복 방지 |
| start_additional_order | 과거 주문 보존, 같은 좌석 새 주문 | 복사 내역 재확인 |
| get_order_status | 확정/대기/오류 뒤 실제 상태 확인 | 주문 소유권 |

실제 도구에 바인딩하기 전 위 함수명을 모델에 실행 가능 도구로 노출하지 않는다. Function calling에서 JSON 형식이 유효해도 서버가 모든 비즈니스 규칙을 다시 검증한다.
반환 공통 권장: success, error_code, operation_id, cart_version, actual_state, quote, source_ids. 도구 실패 시 이전 상태 보존, 실패 메시지 생성. 빈 tool_results에서 '담았습니다' 생성 금지.
상태 예시: draft → awaiting_confirmation → confirmed_demo. 주류는 verified되지 않으면 pending_staff_check; 확인 뒤에도 최신 내역에 대한 고객 확정 필요. real_payment_status는 not_supported다. 결제 성공 상태와 confirmed_demo를 섞지 않는다.

## 4. 검색 문서 조립
- 실제 카탈로그 RAG: 메뉴목록+가격영양은 menu_id/variant_id로 결합한다. 가격영양에는 menu_id 열이 없으므로 variant_id 접두부로 정규화하고 메뉴목록과 무결성 검증한다.
- menu 문서: 이름/별칭/설명/재료/알레르기/기본 맛/추천 태그/페어링/판매 단위.
- variant 문서: 정확한 variant_id/온도/크기/용량/가격/기본 샷/카페인/영양/도수.
- bean/option/policy/bilingual은 별도 유형으로 저장. 옵션은 적용 메뉴와 조건을 반드시 함께 넣는다.
- 비교는 대상마다 검색, 옵션은 해당 메뉴의 option+variant, 알레르기는 재료+milk 규칙+P09, 주류는 variant+P15+P19를 검색한다.
- 검증질문은 평가 전용으로 분리한다. 기대답이 검색돼서 테스트를 맞히는 누수를 막는다. 선별내역은 역사 기록이므로 현재 판매 카탈로그로 인덱싱하지 않는다. 사진은 실제 성분/제공량 증거가 아니다.
- 점수 임계값은 개발 팀이 retriever 거리/유사도 의미와 정규화 방식을 확인한 뒤 평가 세트로 설정한다. 공통 숫자를 임의 지정하지 않는다. 낮은 점수/근거 누락이면 정확 ID 조회나 재검색 후 확인 불가 답변으로 전환한다.

## 5. 금액·카페인 단위 검증 예
Q04: M03-ICED-L 6500 + B03 700 + oat 500 + extra_shots2×600 = 8900원/잔, 2잔17800원. 기본3샷+추가2샷, B03 샷당4mg →20mg/잔. 주요 영양은 미산정.
Q09: M08 기본2샷, B03 →2×4+카카오12=20mg. 원두 변경 후 주요 영양 미산정.
Q35: 50ml×0.20÷190ml≈5.3%; 얼음 포함300ml를 분모로 쓰지 않는다. 고객 답변은 문서 시연값이며 안전 음주 기준이 아님을 구분한다.

## 6. JSON 사용 규칙
04 파일은 OpenAI 응답의 json_schema 설정 내부에 전달할 schema 본문이다. 사용하는 SDK/API 버전의 래퍼는 개발 팀에서 적용한다. strict 형식 사용 시 모든 필수 키와 nullable 값 준수. 예시는 특정 API 버전 실행 검증이 아니다.
- options의 null은 미지정이다. 기존 cart 수정 시 null로 기존 옵션을 지우지 않는다. 서버가 적용 가능 기본값을 채운다.
- needs_clarification이 true이면 모든 복합 쓰기를 보류한다. blocked_reason이 있거나 참조가 미해결이면 같은 원칙.
- 재작성 resolved=true는 원문의 지시 대상 해결을 뜻할 뿐 주문 필수값/옵션 검증 완료가 아니다.
- tool 성공/수락 검증/직원 인증은 모델 출력에서 만들지 않는다.
