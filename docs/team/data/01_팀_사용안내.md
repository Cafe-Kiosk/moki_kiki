# 모키 커피바 v4 팀 사용안내

> 데이터팀 v4의 기존 안내를 보존한 사본입니다. 이번 GitHub 묶음에는 안내·JSON·JSONL을 포함합니다. [엑셀 원장](../../../data/moki_data.xlsx)은 저장소 data/에 있으며 사진 33장이 내장되어 있습니다. 아래의 images/·image_prompts.json·원본 XLSX 파일명은 기존 배포 묶음의 구성 설명이며 이 폴더의 파일 목록이 아닙니다. 별도 PNG·브라우저 발표·환경 전용 시작 파일의 중복 업로드는 생략했습니다.

2026-10-14 · 엑셀·JSON·RAG·이미지는 같은 v4 묶음으로 교체한다.

## 먼저 확인할 내용

간장버터 버섯구이(M30)·김부각(M31)을 삭제했다. 분류는 **커피 / 차·논커피 / 디저트 / 주류 / 원두** 5개다. 데이터의 정확한 두 번째 분류 값은 `차/논커피`다. 주류는 6종으로 늘렸다. 한국 재료 메뉴를 별도 분류로 보여주지 않는다.

엑셀 **사진메뉴판**에서 전체 구성을 보고, **메뉴목록**, **가격영양**, **옵션규칙**, **매장정책**을 순서대로 확인한다. **한영안내**에는 전체 영어 설명과 재료 용어집이 있다. **검증질문** 47개는 실제 팀 앱에서 실행할 시험안이다.

| 파일 | 내용 |
|---|---|
| `모키_커피바_데이터_v4.xlsx` | 10개 탭, 통합 분류와 주류 계산, 사진 33장 내장 |
| `mokey_data.json` | 메뉴 33개, 주문 조합 52개, 원두 3종, 옵션 6종, 정책 19개, 검증 질문 47개 |
| `rag_documents.jsonl` | 한국어 61개·영어 61개, 총 122개 문서 |
| `images/` | 현재 판매 메뉴별 대표 PNG 33장 |
| `image_prompts.json` | 사진별 프롬프트·상대경로·대표 주문 ID·SHA-256·생성 도구 |
| `00_컨셉과_단계별_구상.md` | 수정 판단과 단계별 구성 |
| `02_검토와_변경내역.md` | 수정한 오류와 검증 범위 |

사진은 내장 `image_gen`으로 만든 AI 연출 이미지다. PNG는 `images/`에, 엑셀에는 같은 이미지의 축소 JPEG 사본을 넣었다. 폴더 전체 또는 ZIP을 전달해야 상대경로가 유지된다. 이 작업에서 팀 채팅으로 직접 발송하지 않았다.

## v3에서 교체할 때

1. `menus`와 `variants`를 현재 주문 가능한 목록으로 사용한다. M30·M31은 v4에서 제외했고, 과거 제외된 M19·M22도 계속 주문할 수 없다. M34~M37이 신규 주류다. 기존 ID를 다른 메뉴에 재사용하지 않았다.
2. 제외 메뉴가 장바구니에 남아 있으면 다시 선택하도록 한다. 삭제된 음식을 다른 음식으로 자동 치환하지 않는다.
3. RAG 인덱스는 **교체**한다. 옛 문서에 추가 적재하면 삭제 메뉴나 옛 분류·정책이 검색될 수 있다. 기존 이미지 캐시와 추천 목록도 교체한다.
4. `menu_groups`는 비중복 5개 그룹이다. 예전 `korean`, `food`, `cocktails` 그룹 ID에 의존했다면 새 `coffee`, `tea`, `dessert`, `alcohol`, `beans` 목록으로 변경한다.
5. `schema_version=4`다. 엑셀·JSON·JSONL은 같은 빌드의 스냅샷이며 한 파일을 수동 편집해도 다른 파일이 자동 갱신되지 않는다.

## 주문과 한영 안내

가격과 합계는 `variants` 및 `option_rules`로 코드에서 계산한다. 수량은 1~10의 정수이며, 허용 메뉴·온도·크기·옵션을 먼저 검증한다. 사진의 온도나 크기만 보고 주문 조합을 만들지 않는다.

`하이볼`과 `highball`은 M32와 M34의 공통 별칭이다. 두 후보 중 선택을 확인한다. `decaf iced latte`처럼 구체적인 별칭은 `alias_attributes`의 ICED와 원두 B03을 함께 반영한다. 언어를 바꿔도 메뉴 ID·좌석·수량·옵션·주류 확인 상태를 유지한다.

메뉴는 한국어 문서 `M01`, 영어 문서 `M01:en`처럼 연결한다. 같은 `entity_id`가 같은 메뉴이며 `lang`으로 표시 언어를 선택한다. 이름뿐 아니라 맛·식감·재료·알레르기·판매 단위를 보여준다. 국적이나 언어로 취향을 추정하지 않는다.

약과 수량 1은 2개 1접시, 쑥인절미 수량 1은 4개 1접시다. 맥주는 330ml 1잔, 와인은 150ml 1잔이다. `ICED`는 차갑게 제공하는 코드이며 M35 마티니와 M36 맥주에는 얼음이 없다. M37 와인의 `NA`는 온도 선택 없음이다. `NA`를 무조건 음식으로 해석하면 안 된다.

## 주류와 카페인

`contains_alcohol=true`인 M32~M37 모두 직원 확인 규칙을 적용한다. 고객의 체크박스나 챗봇 응답은 직원 확인이 아니다. 해당 주문에서 실제 마실 손님의 확인 전에는 `pending_staff_check`를 유지한다. 실패하면 확정할 수 없다. 기존 `alcohol_order_contract`를 직원 측 처리와 연결해야 하며, 실제 확인 화면·API는 이 데이터 작업에서 구현하지 않았다.

주류는 고정 레시피·판매 단위·매장 이용만 지원한다. 샷·원두·우유·얼음 변경, 술 제거, 포장은 지원하지 않는다. 주류 추천은 손님이 원하는 경우에만 하고 자동으로 담지 않는다. 비주류 대안은 별도 메뉴이며 선택을 확인한다. 대안이 원래 술과 같은 맛·카페인 함량이라는 뜻은 아니다.

마티니는 에스프레소 1샷 60mg + 커피 리큐르 10mg = 카페인 **70mg**으로 설정했다. 디카페인·샷 변경 옵션은 없다. 기존 키 `caffeine_non_coffee_mg`는 이제 **에스프레소 외 카페인**이라는 의미로 읽어야 한다. 마티니에서는 커피 리큐르 카페인도 이 값에 포함된다.

맥주에는 보리, 와인에는 아황산류를 표시했다. 알레르기 목록이 비었다고 안전하다는 뜻은 아니며, 공용기구 교차접촉 가능성이 있다. 가격·성분·영양·카페인은 모두 가상 매장 레시피 설정이다.

## 도수·열량 계산

`alcohol_components`의 원액별 `volume_ml × abv_percent / 100`을 합산하면 순알코올 부피다. 이를 `liquid_volume_ml`로 나눈 뒤 100을 곱하면 도수다. JSON의 `abv_percent=16.7`은 16.7%이며, 엑셀은 0.167 같은 비율을 백분율로 표시한다.

에탄올 질량은 순알코올 ml × 0.789를 소수 둘째 자리로 반올림한다. 열량은 탄수화물×4 + 단백질×4 + 지방×9 + 반올림한 에탄올 질량×7을 정수로 반올림한다. 원두 상품의 1잔 영양은 null이다. 비주류의 도수 null을 0% 인증으로 바꾸지 않는다.

마티니는 40% 보드카 40ml와 20% 커피 리큐르 20ml를 함께 계산한다. 순알코올 20ml, 에탄올 15.78g, 기준 액체 120ml이므로 약 16.7%, 열량은 182kcal다. 기준 액체에는 가정한 셰이킹 희석수 20ml가 들어 있다.

`spirit_volume_ml`·`spirit_abv_percent`는 v3 호환용 첫 증류주 값이다. **전체 알코올 계산에 이 두 필드만 사용하면 안 된다.** 맥주·와인에서는 두 값이 null이다. 새 계산은 `alcohol_components`를 사용한다. 엑셀 가격영양 V/W열은 첫 원액, Y/Z열은 두 번째 원액, U열은 계산 기준 액체량이며 X열에 배합을 설명했다.

합계 확인 예: 마티니 12,000 + 치즈케이크 6,800 = **18,800원**. 라거 2잔 14,000 + 와인 2잔 18,000 = **32,000원**.
