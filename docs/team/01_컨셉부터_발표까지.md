## 1. 컨셉: 어떤 손님이 어디에서 무엇을 하는가

### 처음의 문제와 바뀐 방향

초기 카페 키오스크에서 출발해 **테이블에 앉아서 충분히 질문하고 주문하는 커피바**로 사용 장면을 바꿨다. 메뉴판을 보고도 라떼와 카푸치노의 차이, 오트 변경 가능 여부, 낯선 한국식 메뉴의 맛을 알기 어려운 상황에 초점을 맞췄다. 계산대 앞에서 바로 고르게 하기보다, 질문 → 비교 → 선택 → 수정이 이어지는 자리를 설정한 것이다.

이 방향은 [팀 컨셉 변경 공지][v3], [프로그램 컨셉 문서][concept], 최종 발표 2~4장에서 서로 연결된다. 계산대 대기 감소나 매출 증가는 측정한 성과가 아니라 설계 가설·목표다.

### 메뉴를 늘리는 것과 선택을 돕는 것을 함께 설계

v3 구상에서는 익숙한 커피에 한국 차·다과·가벼운 칵테일을 연결하고, 영어 이름뿐 아니라 맛·식감·재료·판매 단위를 설명하려 했다. [v4 구상][v4-concept]에서는 버섯구이·김부각을 삭제하고, 메뉴를 커피·차/논커피·디저트·주류·원두의 다섯 분류로 정리했다. ‘한국의 맛’이라는 중복 분류도 없앴다. 주류는 여섯 종류로 조정했다.

최종 서비스는 가상 커피바이며 좌석 1~12, 한국어·영어, 비주류의 매장 이용·포장 선택을 지원한다. 실제 결제·매장 접수는 연결하지 않고, 최종 내역에 동의하면 시연 주문번호를 발급한다. 주류는 직원 확인 대기까지다. 음악 신청은 발표 마지막 장의 향후 방향에 남겼다.

**이 단계의 결과:** 누가·어디서·무엇을 할 수 있는지, 무엇을 이번 시연 범위로 삼을지에 대한 공통 기준.

**열어볼 자료:** [컨셉과 구현 범위][concept] · [컨셉 변경 공지][v3] · [v4 수정 판단][v4-concept]. 최종 발표 대응은 1~4장이다.

## 2. 데이터: 모키가 사실로 사용할 메뉴판과 규칙 만들기

### 메뉴 이름만으로는 주문할 수 없었다

‘카페 라떼’라는 이름 외에도 온도·크기별 가격, 기본 원두와 샷, 변경 가능한 우유, 추가금, 카페인, 재료, 알레르기 안내가 필요했다. 질문에 답할 자료와 실제 주문을 계산할 자료를 같은 버전으로 준비했다.

이번에 엑셀을 직접 읽어 확인한 구성은 다음과 같다.

| 자료 | 수 | 역할 |
|---|---:|---|
| 메뉴 | 33 | 커피 12·차/논커피 7·디저트 5·주류 6·원두 상품 3 |
| 판매 구성 | 52 | 메뉴에 따라 HOT/ICED, S/L, 단일 구성 등 실제 판매 가능한 조합 |
| 원두 정보 | 3 | 원산지 설정·로스팅·맛 노트·카페인 등 |
| 옵션 규칙 | 6 | 원두·추가 샷·우유·단맛·얼음·데우기 |
| 매장 정책 | 19 | 좌석·이용 방식·확정·미지원 기능·주류 등 |
| 데이터 검증 질문 | 47 | 앱에 물어보고 기대 행동을 확인할 시험안 |
| 대표 이미지 | 33 | 가상 메뉴의 AI 연출 사진 |

메뉴 33개와 원두 정보 3개는 다른 표의 개수다. 메뉴의 ‘원두 상품 3종’과 원두 자체의 설명 레코드를 구별해야 한다. 판매 구성 52개도 메뉴 52개라는 뜻이 아니다.

### 엑셀 10개 시트가 맡은 일

| 시트 | 확인할 내용 |
|---|---|
| 메뉴목록 | 메뉴 ID·이름·분류·별칭·맛 점수·재료·알레르기 |
| 가격영양 | 판매 구성별 온도·크기·가격·카페인·영양 |
| 원두 | 원두별 맛·로스팅·카페인·연결 상품 |
| 옵션규칙 | 메뉴별 허용 옵션과 추가금·제한 |
| 매장정책 | 주문·주류·확정·미지원 범위 |
| 검증질문 | 질문과 확인할 기대 행동 |
| 선별내역 | 메뉴를 유지·제외한 판단 |
| 설계근거 | 참고 자료와 가상 설정의 경계 |
| 사진메뉴판 | 메뉴 사진과 대표 정보 |
| 한영안내 | 한국어·영어 설명과 재료 용어집 |

실제 답변·가격·주문 규칙에는 메뉴·가격·원두·옵션·정책·한영 정보가 쓰인다. 검증질문의 정답은 평가용이므로 RAG 검색에 넣지 않는다. 사진도 가격과 가능한 옵션을 결정하는 원장이 아니다.

### v4에서 실제로 정리한 부분

삭제한 메뉴는 판매 구성·사진·페어링·RAG에서도 함께 제거했다. ‘하이볼’은 유자 소주 하이볼과 위스키 하이볼 두 후보가 있으므로 확인하도록 했다. `ICED`가 얼음 포함을 뜻하지 않는 마티니·맥주, 온도 선택이 없는 와인도 구별했다. 주류 여부와 카페인 여부를 독립적으로 설명했다. 가격·영양·도수·사진은 실제 브랜드의 실측값이 아니라 시연용 설정이다.

### 데이터팀 문서 122개와 앱 문서 61개의 관계

팀 전달용 [rag_documents.jsonl][jsonl]은 한국어 61개+영어 61개로 총 122개다. 로컬 앱의 [문서 생성 코드][documents]는 엑셀을 읽어 메뉴 33+원두 3+옵션 6+정책 19=61개 문서를 만들고, 각 문서에 한영 정보를 함께 묶는다. 따라서 숫자가 다르다고 절반을 누락했다고 볼 수 없다. 현재 앱은 전달 JSONL을 그대로 적재하는 경로 대신 엑셀에서 문서를 만드는 경로를 쓴다.

**이 단계의 결과:** 검색과 주문 코드가 공유할 판매 사실·허용 규칙·한영 설명, 그리고 별도로 관리하는 평가 질문.

**열어볼 자료:** [데이터 v4 엑셀][xlsx] · [구조화 JSON][data-json] · [팀 전달 RAG 문서][jsonl] · [v4 사용안내][data-guide] · [데이터 수정·검증 기록][data-review]. 최종 발표 대응은 4~8장이다.

## 3. HTI: 손님이 해야 할 일을 빠짐없이 나누기

HTI는 Hierarchical Task Inventory로, 큰 목표에 어떤 세부 행동이 포함되는지 정리한 목록이다. ‘가격을 비교하기’와 ‘수량을 바꾸기’는 손님의 과업이며, 임베딩·검색·JSON 분류는 프로그램 내부 처리다. HTI의 가지는 고정된 실행 순서가 아니다. 메뉴를 정한 손님은 바로 주문할 수도 있다.

### 여러 초안을 최종 원문과 연결

작업 폴더에는 131개 검토안, 20개 요약안, 개발용 55개 말단 과업 대응표가 남아 있다. 이들은 서로 다른 시점·목적의 자료다. 최종 발표를 설명할 때 모두를 현재 확정 HTI로 합쳐 말하면 범위가 커진다.

10월 15일 저장된 원문 서식 확인에서는 G·H와 하위 항목 전체가 취소선이다. 따라서 최신 16장 발표는 아래 **A~F**를 기준으로 한다. 이번 검토에서는 저장된 원문 확인 기록을 읽었고 Google Drive를 새로 조회하지는 않았다.

| 최종 발표의 상위 과업 | 대표 행동 |
|---|---|
| A. 주문 시작하기 | 대화 시작·좌석 확인·언어와 보기 설정 |
| B. 메뉴 탐색하기 | 이름으로 찾기·추천받기·정보 확인·맛과 가격 비교 |
| C. 메뉴 선택 및 옵션 정하기 | 메뉴·온도·크기·원두·우유·샷 선택 |
| D. 장바구니 관리하기 | 담기·수량과 옵션 수정·삭제·총액 확인 |
| E. 이용·수령 방식 정하기 | 매장/포장·컵·포장 용품 관련 과업 |
| F. 결제하기 | 최종 내역·결제·주문 완료 관련 과업 |

### 설계 범위와 구현 범위의 차이를 남겼다

원문에는 한·영·중·일, XL, 샷 +3, 컵과 포장 용품, 할인·적립·결제 방식 등이 포함된다. 현재 앱의 지원은 한·영, 데이터에 있는 S/L·단일 구성, 추가 샷 0~2 등이다. 실제 결제·할인·영수증은 미지원이다. F는 최종 내역 검토 → 시연 확정 → 번호 확인으로 시연한다.

추가 주문·취소·되돌리기 중 일부는 앱에 구현돼 있어 소개할 수 있지만, 취소선 처리된 G·H의 확정 과업으로 소개하지 않는다. 예전 [개발 HTI 대응표][dev-hti]는 A~H를 유지하므로 최신 발표의 A~F를 설명할 때는 [최종 원문·시연 대응][hti]를 우선한다.

### HTI를 시연으로 바꾼 방법

| 과업 | 시연 입력·결과 |
|---|---|
| B4.1 맛·가격 비교 | ‘아메리카노랑 카푸치노 가격·진하기 차이는?’ |
| C2.2 크기 선택 | 크기가 빠지면 질문 → ‘라떼는 작은 걸로요’ |
| D1.1 담기 | 디카페인 라떼+약과 10,700원 |
| D2.1 수량 변경 | ‘라떼만 하나 더’ → 16,900원 |
| D3.1·F2.1 내역 확인 | 메뉴·옵션·수량·합계를 확인 |
| F3.1 번호 확인 | 명시적 수락 뒤 시연 주문번호 확인 |

**이 단계의 결과:** 사용자 목표 → 필요한 동작 → 시연 입력 → 확인할 결과의 연결.

**열어볼 자료:** [최종 HTI 원문과 시연 대응][hti] · [이전 개발용 상세 대응 CSV][hti-csv]. 최종 발표 대응은 11~13장이다.

HTI 계층도는 발표 PDF 11장에서 확인합니다.

## 4. 개발: 자료·대화·장바구니를 한 앱으로 연결하기

### 첫 개발본에서 발견한 간극

10월 14일 작업현황에는 새 프롬프트와 기존 앱의 입출력 구조 차이, 일부 옵션 제한의 저장 단계 누락, 확정 후 같은 주문 변경, 고객 체크와 직원 확인의 혼동 등이 기록돼 있다. 당시 시험표 67개는 NOT_RUN이었다. 이 초기 상태와 이후 수정본의 시험 결과는 구별해야 한다.

### 최종 실행본의 처리 흐름

1. **화면:** Streamlit에서 질문·좌석·언어·이용 방식·현재 주문을 표시한다.
2. **요청 해석:** 사용자 문장에서 메뉴·옵션·수량·여러 행동을 추출한다.
3. **자료 검색:** 이름·별칭, 맛 점수, 임베딩과 FAISS를 함께 사용한다. 비교 질문이면 양쪽 자료를 확보한다.
4. **규칙과 계산:** 판매 구성·메뉴별 옵션·정수 수량을 검증하고 단가와 합계를 코드로 계산한다.
5. **응답:** 검색 근거와 실제 처리 결과를 AI에게 함께 전달한다.
6. **상태 반영:** 복합 변경은 복사본에서 검증하고 성공한 상태를 반영한다. 오류가 나면 일부만 담긴 주문이나 중복 처리를 방지한다.

현재 기본 모델 설정은 요청 해석·응답에 `gpt-4.1-mini`, 임베딩에 `text-embedding-3-small`이다. 이 설명은 코드 기본 설정이며 실행 환경에서 변경할 수 있다.

메뉴·정책 문서는 ‘매장에서 무엇을 파는가’를 설명한다. 대화 기록은 ‘앞에서 무엇을 말했는가’를 잇는다. 현재 장바구니는 ‘지금 구성 중인 주문’을 보관한다. 확정 주문은 ‘이미 확인한 과거 내역’을 보존한다. 이 구분 덕분에 영어로 바꿔도 주문을 보존하고, 확정 후 추가 주문을 과거 주문에 덮어쓰지 않는다.

### 금액 계산 예

큰 아이스 라떼 6,500원+디카페인 700원+오트 500원+추가 샷 2회 1,200원=한 잔 8,900원. 두 잔은 17,800원이다. 프롬프트가 스스로 최종 금액을 정하는 방식이 아니라 코드가 계산한 결과를 응답과 주문 내역에 함께 쓴다.

### 수정 뒤 남은 실행 근거

저장된 시험 결과는 오프라인 회귀·화면 검사 42개, 기존 계산·규칙 검사 26개, 원래 질문 67개 실제 API 실행과 영향 사례 재시험, 연속 대화 3개·14턴이다. 67개 판정은 핵심 기준 확인 57·확인 질문/재선택 8·원안과 제안 차이 2다. 마지막 코드에서 67개를 한 번에 전부 재실행했다는 뜻은 아니다.

10월 15일의 초기 실행 기록에는 API 잔액 부족으로 대화가 막힌 시도가 있다. 이후 별도의 실제 API 브라우저 시연 기록에는 비교·크기 확인·수량 추가·확정·새 주문·추천 등 8턴이 저장돼 있다. 성공 기록과 실패 기록을 함께 남겼다. 추천 뒤 현재 주문이 바뀌지 않는 것도 확인했다.

## 5. 프롬프트: AI가 자료를 어떻게 해석하고 설명할지 정하기

프롬프트 작업은 개발 이후 한 번 붙인 문장이 아니다. 데이터와 HTI를 받아 초안을 만들고, 개발 입출력과 연결하고, 실패 사례를 반영하는 과정이었다. 회의록에 기록된 분담은 데이터 류성환·오승재, 프롬프트 안나량·이주연, 개발 박채원·신기훈이다. 이는 담당 기록이며 각 수정의 실제 수행자를 전부 증명하는 자료는 아니다.

### 프롬프트팀의 원래 전달물

프롬프트팀 전달 묶음 안내에는 시스템 프롬프트, 질의 재작성, 복합 의도 분류, JSON Schema, 경계 사례 few-shot 19개, 시험표 67개, 개발 전달안, 시연 문안이 있다. 67개는 데이터 질문 47개에 예외·상태 회귀 20개를 더한 것이다. 원안의 실행 상태는 NOT_RUN이며 개발 전달 문서도 합의 제안이라고 명시했다.

### 최종 프로그램에 연결한 방식

| 실제 실행 프롬프트 | 맡는 일 |
|---|---|
| [system.txt][system] | 근거 제한·추천·옵션·상태·언어·미지원 범위를 지키며 답변 |
| [router.md][router] | 재작성과 복합 행동 분류를 한 호출로 처리 |

최종 실행본은 재작성과 분류를 별도 호출 두 개로 그대로 옮기지 않고 통합 라우터로 연결했다. 출력은 JSON으로 받아 코드의 Pydantic 모델로 검증한다. 팀 원안의 모든 함수·입력 필드·few-shot을 그대로 구현·주입했다고 설명해서는 안 된다.

`prompts/system.md`는 현재 안내 파일이고 실제 시스템 본문은 `system.txt`다. 로더가 `.txt`를 먼저 읽는 것을 소스에서 확인했다. 시스템 본문은 팀 원안과 동일하며, `chain.py`에서 화면 기능·미지원 범위 등 실행 조건을 추가한다. 따라서 원안 본문과 실제 호출의 전체 시스템 메시지는 구별해야 한다.

### 프롬프트가 지키게 한 핵심 행동

- 검색 자료에 없는 가격·옵션·재고·인기 순위를 만들어 말하지 않는다.
- 추천·정보 문의만으로 장바구니에 담지 않는다.
- 조건이 빠지면 질문하고, 후속 답변을 미완료 주문과 연결한다.
- ‘총 두 잔’과 ‘두 잔 더’를 구별한다.
- 코드의 성공 결과가 없으면 담기·변경·확정이 끝났다고 말하지 않는다.
- 언어 전환 시 주문 조건을 보존한다.
- 고객의 말만으로 직원 확인을 완료하거나 실제 결제했다고 말하지 않는다.

예를 들어 ‘작은 걸로요’는 새 메뉴 주문이 아니라 앞서 빠진 크기 답변이다. ‘하이볼 하나’는 후보가 두 개이므로 다시 묻는다. ‘XL로 주세요’는 데이터에 없는 구성을 임의로 L로 바꾸지 않고 제한과 가능한 선택을 안내한다. 이런 지시와 별개로 주문 코드에서도 다시 검증한다.

**이 단계의 결과:** 자연어 요청·검색 근거·실제 상태·응답을 연결하는 행동 규칙과 출력 계약.

**열어볼 자료:** [프롬프트팀 개발 연동 원안][prompt-guide] · [개발 연동 제안][handoff] · [실제 응대 프롬프트][system] · [실제 통합 라우터 프롬프트][router] · [실제 프롬프트 로더][prompt-loader]. 최종 발표 대응은 6~10장이다.

## 6. 발표자료: 만든 기능을 청중이 이해하고 확인하게 정리하기

### 초기 설명에서 최종 16장으로

초기 노트북·발표자료와 이후 14장 리디자인이 작업 폴더에 보존돼 있다. 최신본은 16장이다. 최종 편집 검토 기록에는 커피바 선정 이유 보강, 검색 요약과 상세 근거 구분, 세 가지 검색 방식, 요청 해석과 주문 처리의 역할, 취소선 없는 HTI 반영이 기록돼 있다. Manus·Claude 참고자료의 아이디어도 선택적으로 반영했으며, 참고자료를 그대로 최종 사실로 삼지는 않았다.

### 최종 발표의 구성

| 장 | 청중에게 설명하는 내용 | 앞 단계의 근거 |
|---|---|---|
| 1~4 | 모키 소개·손님 질문·커피바 이유·낯선 메뉴 안내 | 컨셉과 한영 메뉴 자료 |
| 5 | 라떼의 설명·가격·옵션 | 데이터 v4 |
| 6~8 | RAG 필요성·요약/상세 근거·이름/맛/의미 검색 | 문서 생성·검색 코드 |
| 9 | 요청 해석→검색/주문 처리→답변과 화면 | 실제 개발 구조 |
| 10 | 옵션 검증과 17,800원 계산 예 | 가격·옵션 규칙과 주문 코드 |
| 11 | A~F HTI 계층 | 최신 원문 서식 확인 기록 |
| 12~13 | 크기 확인·조건 유지·수량 변경 | 실제 대화와 상태 기록 |
| 14 | 앱 시연으로 이동 | 로컬 시작 파일·시연 순서 |

### 5분 시연은 기능 목록을 읽는 대신 한 주문을 이어간다

메뉴 비교 → 따뜻한 디카페인 라떼+약과 요청 → 누락된 크기 확인 → 10,700원 → 라떼만 추가 → 16,900원 → 최종 내역 → 시연 확정 → 별도 아메리카노 4,500원의 흐름이다. 최종 대본에는 이어서 영어 전환·조회, 시간이 남으면 취소도 제시한다.

10월 15일 실제 브라우저 시연 8턴은 핵심 주문 흐름과 추천을 확인한 기록이다. 최종 대본의 영어 전환·취소까지 같은 8턴 안에 실행됐다는 뜻은 아니다. 해당 상태 전이는 10월 14일 연속 대화 기록에서 따로 확인한다.

### 현재 발표자료에서 알아둘 경계

발표 HTI에는 컵·포장 용품·결제 등이 설계 과업으로 표시돼 있지만 모두 구현된 기능은 아니다. 발표자 자료의 지원 범위를 함께 설명해야 한다. 마지막 두 장은 성공 검사와 향후 운영 방향 위주라, 공식 과제의 ‘약점 및 추후 개선점’ 설명 시간에는 실제 결제·매장 접수 미연동, 한영 범위, 음성·사용성 미검증 같은 한계를 구두로 분명히 연결하는 편이 적절하다. 이번에는 원본 발표를 고치지 않았다.

최종 PPT와 PDF의 해시·장수·PDF 텍스트를 이번에 확인했다. 구조도·HTI 렌더도 직접 열어봤다. 기존 검토 기록에는 전체 렌더·브라우저·링크 검사가 남아 있다. 이를 이번에 모든 화면을 다시 리허설한 것으로 표현하지 않는다.

**이 단계의 결과:** 기존 로컬 산출물은 16장 PPT·PDF·브라우저 발표와 시작 파일이며, 이번 GitHub 묶음에는 PPT·PDF·발표자 설명·HTI 대응·표준 실행 안내를 제공합니다.

## 여섯 단계가 한 주문으로 연결되는 모습

| 단계 | ‘따뜻한 디카페인 라떼와 약과’를 처리할 때 |
|---|---|
| 컨셉 | 테이블에 앉은 손님이 낯선 메뉴를 질문하고 선택한다 |

| HTI | 메뉴·옵션 선택, 담기, 수량 수정, 최종 내역 확인 과업을 정의한다 |

## 기존 전과정 검토에서 한 일과 하지 않은 일

이번에는 최종 파일 식별과 해시 대조, PPT/PDF 16장 확인 및 PDF 텍스트 읽기, v4와 앱 엑셀 10개 시트의 값 대조, 문서 61개 재생성·개수 확인, 전달 JSONL 122개·이미지 33장 확인, 시스템 원안 일치 확인, 핵심 소스 읽기, ZIP CRC와 핵심 파일 일치 확인, 저장된 시험·시연 기록 검토를 했다. [확인 기록][verification]에 결과를 남겼다.

새 API 호출, 67개 전체 재시험, PowerPoint 슬라이드쇼, 음성 청취, 실제 사용자 평가, 팀 공유앱 동등성 검사, 새 환경 설치, 제출·메일 발송은 수행하지 않았다. 저장된 API 성공은 다음 실행의 가용성이나 같은 모델 문구를 보장하지 않는다.
